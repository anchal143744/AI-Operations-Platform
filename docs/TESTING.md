# Testing

## Browser release gate

`e2e/release-gate.spec.ts` defines three Chromium journeys using actual browser
UI: fresh registration/verification/onboarding, workflow definition and
immutable version, approval-gated internal notification, worker completion,
notification read state, filtered audit history and reload persistence;
signed-out access; and a controlled API failure/retry plus rejection path. It
also checks desktop/mobile overflow and browser page/console errors. Test
discovery (`pnpm exec playwright test --list`) is **not** a browser pass.

Run only against a migrated, disposable local PostgreSQL database or schema
that has `test` in its name. The suite requires
`AOP_E2E_DISPOSABLE_DB=true`; it refuses a remote database and launches its own
web/API/worker stack with that `DATABASE_URL` rather than reusing occupied
ports. `AUTH_EMAIL_TRANSPORT=development` is required for the local
verification-code preview. Install Chromium through Playwright on an approved
test host and run `pnpm test:browser`. The suite generates random accounts and
does not clean up its records; never use a personal or production database.
See `docs/DEPLOYMENT.md` for the startup contract. Until the suite actually
runs in Chromium, browser QA and production-readiness remain unverified.
CI installs Chromium and runs this suite after migrating its disposable
`aop_ci_test` PostgreSQL service. A fresh per-job authentication pepper is
generated by the runner rather than committed to the repository.

Run them with `pnpm test:db:integration`, `pnpm test:auth:integration`, `pnpm test:authorization:integration`, and `pnpm test:leads:integration` after applying migrations to that disposable database. Never point them at an unknown development or production database.

## Phase 28 reliability proof

`tests/outbox.test.ts` covers the bounded retry schedule and the secret-reference validator. The disposable-PostgreSQL communication suite proves that an API request atomically queues a message, Activity record, and pending outbox entry; duplicate idempotency keys return the same message; the separate worker advances it through provider acceptance; and a signed provider webhook remains deduplicated and tenant scoped. Migration validation checks the outbox constraints and composite tenant relationships. No test invokes a real provider or resolves a real secret.

Worker failure and crash semantics are architectural invariants: remote delivery is at-least-once, adapters must honor the persisted idempotency key, stale processing leases are reclaimable after five minutes, and retries stop after the third claimed attempt. A production soak/fault-injection suite remains required before connecting a real provider.

The subsequent reliability tests cover exhausted stale leases (no fourth send), non-idempotent ambiguous outcomes (no automatic resend), conflicting idempotency-key reuse, readiness failure, and SES authentication-email command composition using a fake SDK client. They do **not** prove live SES delivery. GitHub Actions starts a disposable PostgreSQL service, deploys migrations, builds the API, then runs the database integration suites; local tests still require an explicitly disposable test-named database. Provider timeout/crash and failover soak testing remains a staging gate.

## Follow-ups, workspace profile, and onboarding proof

`tests/follow-ups-service.test.ts` and `tests/settings-service.test.ts` check tenant-scoped service queries and the cookie-backed frontend API boundary. `scripts/local-auth-smoke.mjs` creates a random isolated schema in the confirmed local `ai_operations` PostgreSQL database, applies all migrations, boots the API on an ephemeral port, and exercises registration, verification, atomic onboarding profile persistence, Follow-up create/list/summary/reschedule/complete, Settings General update/read-after-write, real Team read, and cross-workspace denial. It removes only its own generated schema. Run `node --env-file=.env scripts/local-auth-smoke.mjs` after building shared types and API; never point it at an unknown database URL. This proves local PostgreSQL behavior, not external delivery or production readiness.

Production configuration tests reject the development-only email adapter and an HTTP public app origin. AWS staging must separately test sender verification, IAM permissions, real verification/reset delivery, bounce handling, exact-origin CSRF, secure cookies, and account recovery across web/API domains.

`tests/local-auth-preview.test.ts` verifies that only loopback development can preview a newly issued verification code, that the database receives only its hash, and that a wrong password cannot rotate or reveal a pending account's code. For a local end-to-end check, run `node --env-file=.env scripts/local-auth-smoke.mjs`. It accepts only a loopback `ai_operations` database, creates a randomly named isolated schema, applies existing migrations there, exercises register → verification → session → workspace bootstrap → tenant-scoped Lead creation/listing/status summary and Conversation creation/listing plus CSRF, login, logout, and generic recovery, then removes only that generated schema. Its synthetic records never enter the normal application schema. The broader database integration suites still require a separately provisioned disposable `TEST_DATABASE_URL` containing `test`; a PostgreSQL role without `CREATEDB` cannot provision that database automatically.

## Workflow control proof

`tests/workflow-state.test.ts` checks definition, approval, execution, and policy transitions. `node --env-file=.env scripts/local-auth-smoke.mjs` runs the real Nest/Prisma/PostgreSQL path in a generated disposable schema: workflow create/activate, invalid transition, verified tenant isolation, forged claim rejection, VIEWER write/decision denial, idempotent execution request, policy approval/block outcomes, one decision, transactional outbox creation, audit event, and worker dry-run completion. It removes only its generated schema. This does not prove external side effects, worker crash recovery, scheduler expiry, production deployment, or real AI. The opt-in database integration suites remain separate; skipped tests must be reported as skipped.

The same isolated smoke flow now also covers an approval-gated `INTERNAL_NOTIFICATION`, recipient-only listing and read state, cross-workspace isolation, unique notification creation, and worker-driven approval expiry/cancellation. `apps/api/tests/workflow-worker-reliability.test.ts` covers successful processing, transient bounded retry selection, permanent invalid transitions, and exhausted-lease non-replay. These tests prove local PostgreSQL behavior and worker method behavior, not multi-worker failover, live external delivery, or production reliability. Run the worker separately for manual local use after building the API.

`apps/api/tests/workflow-recovery.integration.test.ts` runs only against an explicitly disposable PostgreSQL target. It proves snapshot immutability and execution pinning, stale `RUNNING`/lease recovery after a simulated crash, concurrent worker claims yielding one notification, transient retry success, and terminal retry exhaustion. The isolated HTTP smoke exercises real worker **processes**, stopping one after a completed dry run and starting a fresh one for the approved notification and Activity path. `pnpm dev` starts web, API, and a locally supervised worker; production readiness requires independent supervision and process-crash/failover soak, not just these deterministic tests.

`tests/worker-operations.test.ts` verifies heartbeat writes and stall thresholds without a database. `apps/api/tests/worker-operations.integration.test.ts` exercises real PostgreSQL heartbeat registration, active/stale/stalled-job detection, and graceful stop, but only in the guarded disposable-schema suite. Local startup additionally checks `/health/worker` after migration. This does not constitute hosted supervision or a multi-host failure soak.

The isolated HTTP smoke also verifies a tenant-scoped workflow Activity query and checks worker readiness before and after a graceful local IPC shutdown. `tests/activity.test.ts` asserts that category/search/workflow filters remain constrained by both tenant IDs. Browser-only accessibility, responsive layout, and console checks require a separate live browser QA pass; API and build tests are not substitutes.

## Planned strategy

- Unit: scoring, policies, transitions, scheduling, validation, permission logic.
- Integration: API/database, authentication, authorization, tenant isolation, transactions, outbox, webhook idempotency.
- AI: schema adherence, extraction accuracy, ambiguity, unsupported claims, injection, failure and version regressions.
- E2E: enquiry through lead, score, draft, approval, send, follow-up, reply, cancellation, audit, analytics.
- Security: unauthenticated/unauthorized access, cross-tenant access, escalation, replay, malicious input, approval bypass.
- Failure: AI/email/database/queue outage, duplicate webhook, worker crash, interrupted workflow, and reply/send races.

Tests use deterministic clocks and provider fakes; E2E runs real PostgreSQL/Redis containers. Critical invariants block merges. Production incidents add regression tests.
