# Workflows

## Current

The backend control slice persists tenant-owned workflow definitions, one versioned policy per workflow, immutable policy evaluations, approval requests/decisions, executions, and one step per execution. The only trigger is manual. Supported actions are `DRY_RUN_LOG` (no side effect) and `INTERNAL_NOTIFICATION` (creates one database-backed notification for the requesting active membership in the same active workspace). Neither action calls an external provider or mutates customer records. Definitions transition `DRAFT → ACTIVE ↔ PAUSED → ARCHIVED`; approvals transition `PENDING → APPROVED/REJECTED/EXPIRED`; executions transition `QUEUED → RUNNING → SUCCEEDED/FAILED` or `WAITING_FOR_APPROVAL → QUEUED/CANCELLED`. New approval requests expire after 24 hours; the separately running outbox worker sweeps expired requests. A blocked policy cancels before outbox enqueue.

`POST /workflows/:id/executions` evaluates policy and records the evaluation and execution atomically. `REQUIRE_APPROVAL` creates a review request; an authorized decision enqueues the existing transactional outbox event. `ALLOW_DRY_RUN` is permitted only for the no-op action; internal notifications require approval. `BLOCK` does not enqueue. The worker owns a lease, uses compare-and-set status updates, and atomically records the step, Activity events, notification (when selected), and completion. Transient workflow failures use bounded outbox retry; exhausted claims fail without replaying a fourth attempt. `(organizationId, workspaceId, idempotencyKey)` prevents duplicate executions; a unique execution reference prevents duplicate internal notifications. All object queries use verified tenant scope; the client cannot submit identity/role/tenant claims. `ExecutionEvent` is the existing append-only `ActivityEvent` contract, not another event store.

The web `/workflows` and `/approvals` routes show real records for a selected verified workspace. `/workflows/:id/versions` exposes tenant-scoped immutable snapshots; execution history exposes pinned version, policy result, step timing, and bounded outbox attempt state without raw worker errors. `/workflows/summary` and `/approvals/summary` feed live dashboard counters alongside the authenticated member's notification unread count. The review queue shows the pinned action and policy result, not merely the mutable current definition. The AppShell notification control reads the member's own notifications, permits marking them read, and links to the originating workflow. These are in-app records, **not email, push, or customer messages**. Visible pages use bounded polling rather than a second event system. `pnpm dev` builds the API and launches web, API, and a supervised local worker. In production the worker remains a separate service; a healthy API does not prove worker health. The builder illustration, AI connection, and broader settings remain conceptual previews. There is no AI evaluation, scheduled trigger, external action, full workflow builder, live provider, general policy rules engine, or production-grade external execution service. Never interpret a successful dry run as a delivered business action.

The minimal persisted rule is one explicit action condition (`WorkflowDefinitionVersion.actionType`) plus one policy effect (`policyMode`) pinned into each immutable definition snapshot. Evaluation is deterministic: `ALLOW_DRY_RUN` allows only `DRY_RUN_LOG`; `REQUIRE_APPROVAL` requests review; `BLOCK` cancels. Even a malformed historical snapshot pairing `ALLOW_DRY_RUN` with `INTERNAL_NOTIFICATION` fails closed. This is deliberately not an arbitrary conditional rules language.

## Versioning and recovery

New executions pin an append-only `WorkflowDefinitionVersion` containing the name, description, trigger, action, and effective policy/version. Draft/paused definition edits and policy changes create a new snapshot. Existing executions retain their earlier version even when the current workflow changes; PostgreSQL rejects updates/deletes to snapshots. Historical executions created before this migration remain explicitly unpinned because their exact past configuration cannot be reconstructed. The current workflow row remains an editing surface, not execution authority. The worker uses the pinned action and content for new internal notifications.

The worker periodically reconciles `RUNNING` executions whose lease is older than five minutes. A pending step can return to `QUEUED` for lease reclaim; a persisted completed step is finalized without replay; inconsistent state fails closed. Every reconciliation writes an Activity event. Outbox claims use `FOR UPDATE SKIP LOCKED`, lock tokens, a three-attempt ceiling, and bounded delays. Local in-database notification creation, step completion, Activity, and outbox completion commit in one transaction; notification uniqueness per execution prevents a duplicate record. This is **not** a claim of exactly-once external delivery. Future provider actions need provider-side idempotency and uncertain-outcome reconciliation.

## Planned V1 workflow

Accepted enquiry → normalized inbound message → schema-validated AI extraction → validated tenant lead → qualification → risk/policy evaluation → response draft → human decision → provider send → persisted delivery state → scheduled waits/follow-ups → inbound reply correlation → atomic cancellation → activity/audit events → analytics projection.

Each instance pins a definition version. Steps have durable state, input/output references, attempts, next run, timeout, idempotency key, and correlation ID. Conditions are deterministic; AI suggestions are stored inputs, not hidden control flow. Workers are retry-safe, and operators can inspect/retry terminal failures without replaying completed side effects.

The frontend `Workflow` contract represents a definition only. A separate execution-summary contract holds run status, timestamps, counts, and failure context. The future backend must keep immutable definition versions and durable execution instances separate; activating a definition is not evidence that any step executed.

Follow-up invariant: at most one active schedule per sequence step, and no automated follow-up may send after the conversation is marked replied. Reply acceptance, schedule cancellation, and send-claim logic must be transactionally coordinated and race-tested.
